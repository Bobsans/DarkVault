# DarkVault v2.0.0

This release adds application-level access protection, mandatory administrator
MFA, typed secret values and configuration projection across the SDKs and CLI.
The server and all SDKs share version 2.0.0. HTTP/JWE remains protocol version 1.

## Breaking changes and upgrade checklist

- Administrator password login now starts a WebAuthn challenge. A passkey with
  user verification is required before an administrator session is issued.
  Register the first passkey in a controlled environment, save the one-time
  recovery codes offline, and use an HTTPS domain supported by your browser.
  Existing login automation must implement the MFA flow.
- Set `DARKVAULT_TRUSTED_PROXIES` explicitly when using HTTPS termination at a
  reverse proxy. Forwarded headers are ignored by default. Direct HTTPS does not
  need this setting. The application does not install or manage a proxy/firewall.
- New tokens default to 30 days, including `expiresAt: null`; the maximum is
  90 days. Existing tokens are also capped at 90 days from their original
  creation date. Inventory and replace older/non-expiring tokens before upgrading.
- Rebuild .NET consumers against the new SDK: public secret records gained type
  metadata, changing constructor/deconstruction binary signatures. Existing string
  access remains available; use typed/configuration APIs when appropriate.
- Go consumers must change imports to `github.com/Bobsans/DarkVault/clients/go/v2`
  and require `v2.0.0`. The repository tag is `clients/go/v2.0.0`.
- Anonymous HTTP traffic and `429` responses no longer write to the vault SQLite
  database. Authentication failures are emitted through `DarkVault.Security`;
  request counters are available through its Meter. Transactional operation audit
  remains mandatory before returning secret values.

Back up the data directory and any external wrapping key separately before an
upgrade. New typed-secret writes use storage format 2; older storage format 1
string values remain readable by this release. Do not downgrade a database after
new writes: roll back by restoring the pre-upgrade backup and reviewing token
revocations made since that backup.

## Access protection

- Network quotas run before token lookup and JWE work; authenticated tokens and
  the administrator also have independent quotas.
- Repeated password, MFA or token failures cause in-process temporary bans with
  escalation. IPv4-mapped addresses are normalized and IPv6 /64s share a quota.
- Passkey challenges and recovery codes are single-use. Sensitive administrative
  operations require recent MFA; factor changes invalidate old sessions.
- Optional AES-256-GCM keyring protection uses an external random key file, with
  no mandatory KMS/TPM dependency. Private files use restrictive Windows ACLs or
  Unix permissions. Existing keyrings require explicit protection configuration.
- Failure of mandatory operation audit prevents a successful secret response.

## Typed secrets and configuration

Secret values support strings, numbers, booleans and null. C#, Python, Go and
TypeScript SDKs expose typed reads and configuration projection. The CLI supports
typed values and configuration output. The administrator UI includes typed value
editing, configuration preview, navigation and audit filtering.

See [security settings](../security.md), [configuration mapping](../configuration.md)
and [the HTTP/JWE contract](../protocol.md) for setup and integration details.
Rate/banning state is process-local and resets on restart. External DDoS protection,
alert delivery, firewall policy and backup storage remain operator responsibilities.
