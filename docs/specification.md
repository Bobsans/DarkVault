# DarkVault: спецификация

Проект в разработке. Единственная реализация — HTTP/JWE-сервер, веб-интерфейс и клиенты.
Сетевой контракт: [protocol.md](protocol.md). Проверки: [verification.md](verification.md).

## 1. Цель и согласованные требования

DarkVault — сервер секретов с веб-интерфейсом одного суперадминистратора,
бакетами, отдельными токенами приложений и клиентами на разных языках.

- Суперадминистратор входит в веб-интерфейс и управляет бакетами, секретами и токенами.
- Клиенты и CLI получают доступ только по токенам длиной ровно 64 ASCII-символа.
- Каждый токен имеет права, ограничения по бакетам и срок действия не более 90 дней.
- Бакет можно прочитать целиком, например для конфигурации приложения в QA.
- SDK доступны для C# и Python. Все SDK и CLI реализуют весь набор операций с бакетами и секретами.
- Секреты дополнительно шифруются в телах запросов и ответов, расшифровка ответа происходит у клиента.
- HTTPS использует автоматически обновляемый сертификат домена;
  клиенты проверяют его через системное хранилище доверия.

Настройки и контракт изменяются по месту в ходе разработки проекта.

## 2. Архитектура

Один ASP.NET Core сервер с API и веб-интерфейсом на одном origin, SQLite-база
и автоматический HTTPS на reverse proxy, например Caddy. Сервер за локальным proxy
слушает loopback; удалённый backend требует TLS. Forwarded headers принимаются
только от явно доверенного proxy.

UI — отдельное TypeScript SPA, упакованное с сервером, с общим модулем JWE: браузер шифрует значения перед отправкой
и расшифровывает ответы. Секреты не вставляются сервером в HTML и начальное состояние
страницы. SDK для C#/Python и CLI на Go используют тот же HTTP/JWE-контракт.

Текущий объём не включает multi-tenancy, обычных пользователей/роли, историю значений,
динамические секреты, автоматический reload конфигурации и кластеризацию.

## 3. Данные и бакеты

### Бакет

Поля: `id` (UUID), `name`, `description`, `revision`, `createdAt`, `updatedAt`.
Имя уникально, 1–63 символа, regex `^[a-z0-9][a-z0-9_-]{0,62}$`.
Примеры: `app_qa`, `app_prod`, `billing_dev`. Имена не являются секретами.
Переименование не входит в текущий объём; описание можно менять.

### Секрет

Поля: `id` (UUID), `bucketId`, `key`, `type`, зашифрованное значение, `revision`, даты.
Ключ — 1–255 байт UTF-8, без управляющих символов. Двоеточие разрешено:
`ConnectionStrings:Main`, `Jwt:SigningKey`. Ключи регистрозависимы на уровне API;
Unicode не нормализуется автоматически. Уникальность: `(bucketId, key)`.
Тип — string (по умолчанию), number, boolean или null. Тип string хранит любой
UTF-8 текст, включая пустую строку и JSON как текст. Другие типы имеют каноническое
строковое представление на wire и преобразуются в native scalar в типизированных
клиентах. Двоичные вложения пока не поддерживаются. Правила типов и сборки JSON/YAML
описаны в [configuration.md](configuration.md).

Начальные лимиты: 64 КиБ UTF-8 на значение; 4096 секретов на бакет;
1 МиБ на UTF-8 JSON нового снимка бакета, включая secrets/types, ключи и escaping.
Ограничения проверяются транзакционно при любой записи, чтобы разрешённый бакет
всегда можно было прочитать целиком. Сетевые лимиты отдельно заданы в protocol.md.

`ReadBucket` возвращает согласованный снимок всех пар ключ/значение и revision.
Пустой бакет возвращает пустой словарь. Частичный результат при ошибке запрещён.
`ListBuckets` возвращает только метаданные разрешённых бакетов.
`ListSecrets` возвращает только ключи, revision и даты, без значений.
Списки постраничные: `limit` 1–200, по умолчанию 100, непрозрачный `cursor`.
Порядок стабильный по ID; при параллельных изменениях списки не обещают snapshot.

`AddSecret` создаёт и возвращает конфликт, если ключ существует.
`UpdateSecret` меняет только существующий секрет; `SetSecret` — явный upsert.
Изменения существующих секретов и описания бакета требуют `expectedRevision`;
upsert с `expectedRevision = 0` означает создание при отсутствии.
Несовпадение возвращает конфликт без записи. Каждое изменение содержимого
увеличивает revision бакета. Revisions выдаёт транзакционный монотонный счётчик БД:
повторно созданный объект не получает старую revision. Удаление и повторное
создание также дают новый UUID; устаревшая команда не затронет новый объект с тем же именем.

По умолчанию удалить можно только пустой бакет. `recursive = true` удаляет бакет
с содержимым одной транзакцией, требует дополнительных прав и expectedRevision
бакета. UI показывает имя и число секретов и требует подтверждения имени.

## 4. Токены и авторизация

### Формат

```text
token = "dv1_" + base64url(CSPRNG(45 bytes), without padding)
length = 4 + 60 = 64 ASCII characters
pattern = ^dv1_[A-Za-z0-9_-]{60}$
```

Префикс обозначает версию формата. Случайная часть содержит 360 бит энтропии.
Токен непрозрачный: это не JWT, в него не встраиваются scopes, срок или имена бакетов.
Не нужно шифровать сам токен для хранения: сервер сохраняет только
`SHA-256(ASCII(fullToken))` с уникальным индексом. Полная случайная строка показывается
единственный раз при создании; повторно прочитать её невозможно.
Формат и длина проверяются до хеширования. Токен нельзя помещать в URL или логи.

Запись токена: `id`, `name`, `tokenHash`, `scopes`, `bucketIds`,
`allBuckets`, `creatableBucketNames`, `createdAt`, `expiresAt`, `revokedAt`,
`lastUsedAt`. Для отображения используются имя и ID, не фрагменты секрета.
`lastUsedAt` — вспомогательная метрика; задержка обновления не влияет на права.

Срок по умолчанию — 30 дней, включая `expiresAt = null`; максимум — 90 дней.
Ранее выданные токены также ограничены 90 днями от CreatedAt. Даты UTC RFC 3339; токен недействителен
при `now >= expiresAt`. Авторизация проверяется для каждого запроса по состоянию БД.
Отзыв запрещает запросы, чья проверка доступа началась после фиксации отзыва;
уже выданные значения нельзя отозвать из памяти клиента.

Права и срок созданного токена неизменяемы: заменить токен можно,
создав новый, переключив приложение и отозвав старый.
Отзыв сохраняет запись для аудита. Токен не используется как ключ шифрования базы
или транспортного содержимого. Утечка bearer-токена позволяет действовать в его правах.

### Матрица прав

| Операция                                  | Обязательные scopes                           |
|-------------------------------------------|-----------------------------------------------|
| `ListBuckets`                             | `bucket:list`                                 |
| `GetBucket` — метаданные                  | `bucket:read`                                 |
| `ReadBucket` — все значения               | `bucket:read` + `secret:read` + `secret:list` |
| `AddBucket`                               | `bucket:create`                               |
| `UpdateBucket` — описание                 | `bucket:write`                                |
| `DeleteBucket` — пустой                   | `bucket:delete`                               |
| `DeleteBucket(recursive: true)`           | `bucket:delete` + `secret:delete`             |
| `ListSecrets`                             | `secret:list`                                 |
| `ReadSecret`                              | `secret:read`                                 |
| `AddSecret`, `UpdateSecret`, `SetSecret`  | `secret:write`                                |
| `DeleteSecret`                            | `secret:delete`                               |
| `GetTokenInfo` — собственные права и срок | Любой действующий токен                       |

Добавляется только `bucket:write` для описания. `secret:write` намеренно объединяет
создание и обновление; отдельные права на них пока не требуются.
Scopes независимы: запись не подразумевает чтение, список не раскрывает значения.
`bucket:read` сам по себе не раскрывает секреты. Неизвестные scopes отклоняются.

Для каждой операции требуются и scopes, и разрешённый бакет. По умолчанию
`allBuckets = false`, список доступных бакетов пуст, никаких неявных wildcard.
UI выбирает существующие бакеты, сервер хранит их UUID. Повторное создание бакета
с прежним именем не восстанавливает доступ старым токенам.

Для `bucket:create` задаётся список точных будущих имён `creatableBucketNames`.
Успешное создание атомарно добавляет UUID в `bucketIds` этого токена и расходует
соответствующее разрешение имени. Конфликт имени ничего не присваивает.
`allBuckets = true` — явная привилегия на все существующие и будущие бакеты;
вместе с `bucket:create` разрешает создание с любым допустимым именем.
Это исключение выделяется в UI, не является настройкой по умолчанию.

Нельзя получить права суперадминистратора или создавать токены через data API.
`token:create`, `admin:*`, `audit:read` клиентам не выдаются. Если позже потребуется
автоматизированная выдача токенов, это отдельная спецификация административного API.
«Полный набор команд SDK» означает весь data API, а не управление администратором.

## 5. Веб-интерфейс и суперадминистратор

Одна учётная запись, без публичной регистрации и пароля по умолчанию.
Первичная настройка — локальная серверная команда с интерактивным скрытым вводом;
по сети незавершённая установка не позволяет захватить аккаунт.
Хеширование пароля и проверка — штатным ASP.NET Core Identity PasswordHasher,
с параметрами текущей поддерживаемой версии; собственный алгоритм не пишется.
Пароль минимум 15 символов, разрешены длинные passphrase до 128 символов.

Веб-вход использует серверную сессию и cookie `Secure`, `HttpOnly`, `SameSite=Strict`.
Сессия: 30 минут бездействия, 12 часов абсолютного срока. Logout, смена и локальный
сброс пароля аннулируют сессии. Есть ограничение попыток входа по аккаунту и IP,
общая ошибка для неверного логина/пароля и CSRF-защита всех изменяющих запросов.
После пароля обязательна WebAuthn MFA с user verification. До завершения MFA
административной сессии нет. Поддерживаются резервные passkeys, одноразовые
recovery-коды и повторное подтверждение важных действий; см. [security.md](security.md).

Экраны:

1. Вход и смена пароля.
2. Бакеты: список, поиск, создание, описание, удаление.
3. Бакет: ключи, добавление/редактирование/удаление; значение скрыто до явного
   «Показать» или «Копировать». Список не загружает значения заранее.
4. Токены: имя, статус, scopes, бакеты, срок, последнее использование, отзыв.
   Создание предлагает профиль «Чтение бакета» и ручной выбор scopes.
   Полный новый токен показывается один раз, потерянный заменяется новым.
5. Аудит: время, субъект, действие, объект, источник, результат, request ID.
   Таблица с раскрытием деталей; серверный поиск, фильтры типа и результата,
   новые события сверху, обновление и загрузка более старых записей.

Навигация использует History API: `/admin/buckets`, `/admin/buckets/{name}`,
`/admin/tokens`, `/admin/logs`, `/admin/settings`. Работают прямые ссылки,
refresh и «Назад/Вперёд»; вход сохраняет целевой маршрут. Фильтры логов находятся
в query string. Сервер возвращает SPA только на известных UI-маршрутах,
неизвестные API-пути и файлы остаются 404. Интерфейс адаптируется к мобильной ширине.

Суперадминистратор имеет полный доступ. Его cookie работает только в `/admin/api/v1`;
bearer-токен — только в `/api/v1`. Нельзя обменять cookie на токен неявно или войти
в UI токеном приложения. Создание токена и просмотр секрета проходят через JWE
в браузере. Пароль входа передаётся обычным HTTPS, без самодельного обмена ключами.

Значения и токены не сохраняются в localStorage, sessionStorage, service worker,
HTML-кэше или телеметрии. Ответы `Cache-Control: no-store`. CSP ограничивает скрипты
собственным origin; сторонняя аналитика и CDN-скрипты на административных страницах
не используются. Все действия доступны клавиатурой, формы имеют labels и ошибки.
Clipboard может жить дольше страницы; UI не обещает надёжно очистить его за пользователя.

## 6. Шифрование и границы доверия

HTTPS аутентифицирует сервер, защищает вход, bearer-токены и загрузку веб-приложения.
JWE дополнительно защищает содержимое сообщений между SDK/браузером и приложением
DarkVault. Алгоритмы и формат заданы в [protocol.md](protocol.md); реализация через
совместимые JOSE-библиотеки, без собственного шифра и собственного обмена ключами.

Сервер DarkVault видит открытые секреты в памяти и суперадминистратор может их читать.
Это не zero-knowledge vault. Доверенный HTTPS proxy видит bearer-токен, может
подменять выдаваемый публичный ключ или JavaScript; JWE не защищает от его активного
захвата. Защита от такого proxy потребует другого доверенного канала/пиннинга и
отдельной модели распространения клиента. Proxy входит в границу доверия.

### Шифрование хранения

Хранение отделено от транспортных ключей и токенов. Значения шифруются AES-256-GCM
под случайным 256-битным ключом данных. Запись содержит `formatVersion`, `keyId`,
nonce 12 байт, tag 16 байт и ciphertext. AAD связывает версию, UUID секрета,
UUID бакета, точный ключ, revision и type (формат 2): UTF-8 JSON-массив в фиксированном порядке,
без пробелов; правила сериализации должны быть зафиксированы тестовыми векторами.

Nonce создаётся CSPRNG для каждой записи. Уникальный индекс `(keyId, nonce)`
дополнительно обнаруживает коллизии с сохраняемыми записями; при конфликте запись
перешифровывается с новым nonce. После 2^20 шифрований создаётся новый ключ данных;
счётчик использований сохраняется и не уменьшается при удалении записей.
Старые ключи остаются для чтения. После восстановления backup новый ключ создаётся
до разрешения записей, чтобы не продолжать откатившийся счётчик.
Ключи данных хранятся в отдельном защищённом keyring вне SQLite, с доступом только
для пользователя сервиса. Бэкап базы и keyring обязателен; одна база недостаточна.
Потеря keyring означает потерю значений. Доступ ко всему серверу снимает эту защиту.

Ротация ключа данных перешифровывает записи пакетами с сохранением старого ключа
до проверки всех записей и политики хранения резервных копий. Ротация или отзыв
API-токена вообще не требуют перешифрования данных. Имена бакетов и ключей,
revision и метаданные остаются в базе открытыми.

## 7. C# SDK и интеграция с ASP.NET Core

Пакеты: `DarkVault.Client` без зависимости от ASP.NET Core и
`DarkVault.Extensions.Configuration` для Microsoft.Extensions.Configuration.
Основной API асинхронный, с `CancellationToken`. Клиент переиспользует HttpClient,
поддерживает его передачу извне; внешний HttpClient не уничтожается клиентом.
Созданный клиентом HttpClient освобождается через Dispose. Конструктор не выполняет IO.

```csharp
using var client = new DarkVaultClient("https://vault.site.com", token);
var secrets = await client.ReadBucketAsync("app_qa", cancellationToken);
builder.Configuration.AddInMemoryCollection(secrets);
```

Адрес без схемы нормализуется в HTTPS, `http://` запрещён. Токен в примере приходит
из секретного источника приложения, не из исходного кода.

```csharp
await builder.Configuration.AddFromDarkVaultBucketAsync(
    "https://vault.site.com", token, "app_qa", cancellationToken);
```

Расширение сначала полностью получает/проверяет словарь, затем один раз добавляет
его в конфигурацию. Ошибка не оставляет частично заполненный provider.
Последний добавленный provider имеет приоритет; последующие providers могут
переопределить значения DarkVault. Это отражается в примере README SDK.
Конфликт ключей без учёта регистра, например `Key` и `key`, — явная ошибка
расширения до изменения конфигурации. API при этом допускает оба ключа.

Первая версия загружает снимок при запуске; нет фонового polling и скрытого
дискового кэша. При недоступности сервера, неверном токене или повреждённом ответе
приложение по умолчанию не запускается. Синхронную сетевую обёртку и sync-over-async
не добавляем; она не нужна для показанного async Program.cs.

Обязательные методы SDK: `AddBucketAsync`, `GetBucketAsync`, `ListBucketsAsync`,
`ReadBucketAsync`, `UpdateBucketAsync`, `DeleteBucketAsync`, `AddSecretAsync`,
`ReadSecretAsync`, `ListSecretsAsync`, `UpdateSecretAsync`, `SetSecretAsync`,
`DeleteSecretAsync`, `GetTokenInfoAsync`. Мутации принимают revisions по контракту.
Для конкурентного редактирования `ReadSecretAsync` возвращает значение и revision;
для удобства `ReadBucketAsync` возвращает `IReadOnlyDictionary<string, string?>`,
а `ReadBucketSnapshotAsync` — тот же словарь с ID и revision бакета.

Ошибки имеют стабильные код, HTTP status и request ID, но не включают токен,
значения или сырые тела. Чтения можно ограниченно повторять с backoff/jitter;
изменения автоматически не повторяются при неопределённом сетевом результате.
Таймаут по умолчанию 30 секунд; редиректы отключены, токен не уходит другому origin.

## 8. CLI и будущие языки

Python SDK — синхронный `DarkVaultClient(server, token)` с контекстным менеджером.
`read_bucket` возвращает словарь, остальные методы сохраняют metadata и revisions
из wire-контракта. Стандартная библиотека обслуживает HTTPS, `jwcrypto` — JWE.
Набор операций совпадает с C# SDK; собственных crypto-форматов и административного
входа в Python-клиенте нет. [Описание API](../clients/python/README.md).

CLI на Go использует тот же HTTP/JWE-протокол. Команды:

```text
darkvault bucket add|get|list|read|update|delete
darkvault secret add|get|list|update|set|delete
darkvault token info
darkvault config set|get|unset|list|path
darkvault exec --bucket app_qa -- <program> <args...>
```

CLI сохраняет `server`, `token`, `timeout` и `page-size` в приватном пользовательском
JSON-файле. Флаги перекрывают окружение, окружение перекрывает конфиг. `get/list`
маскируют токен. `config set token <token>` сохраняет токен; скрытый ввод и stdin
также поддерживаются. Токен можно передать разово через `--token`, `--token-file`
или окружение. Подробный контракт — в [operations.md](operations.md#cli).
Значение секрета — скрытый ввод или stdin.
`bucket read --format json` явно выводит расшифрованные значения в stdout;
обычные list-команды их не показывают. Ошибки в stderr, ненулевой exit code.
Не вводим `eval`-экспорт и генерацию shell-кода с секретами.

`exec` получает бакет и добавляет переменные только дочернему процессу, затем
возвращает его exit code. Системное окружение и родительский shell не меняются.
Преобразование ключей `:` → `__` включается явно через `--aspnet-keys`.
Ключи вне `[A-Za-z_][A-Za-z0-9_]*`, NUL в значении и коллизии преобразования
отклоняются до запуска. Конфликт с окружением требует `--overwrite-env`;
токен DarkVault из окружения по умолчанию не наследуется дочерним процессом.
Так же ASP.NET-приложению предпочтительно добавлять configuration provider,
а не менять глобальные переменные собственного процесса.

SDK других языков не обязаны повторять C# типы. Обязательны одинаковые wire-format,
семантика scopes, ошибок, pagination, Unicode и revisions. Типы дат, словарей и
криптографические ключи не сериализуются в .NET-специфичные форматы.

## 9. Аудит и эксплуатация

Аудит в SQLite содержит каждый HTTP-запрос, дошедший до приложения: время UTC,
UUID и тип токена/администратора, имя токена, IP клиента и непосредственного
соединения, HTTP-метод и путь без query string, статус, длительность и результат.
Неаутентифицированные запросы имеют principal `anonymous`; неизвестный отправитель
не идентифицируется по предъявленному неверному токену. IP клиента берётся из
Forwarded Headers только для `DARKVAULT_TRUSTED_PROXIES`; IP соединения хранится отдельно.

Команды дополнительно фиксируют UUID и имена объектов, ревизии, ожидаемую ревизию,
флаг recursive, объекты возвращённой страницы или удалённого бакета и выданные права
нового токена. Операция и завершение HTTP-запроса связаны через `traceId`; JWE-команда
сохраняет свой `requestId`. Успешные команды и их audit-события фиксируются атомарно.
Завершения аутентифицированных запросов, кроме `429`, также записываются в БД.
Анонимный трафик и `429` учитываются метрикой; отказы проверки credentials —
структурированным журналом безопасности, без записи на каждый отказ в SQLite.
Успех команды означает выполнение на сервере,
а не подтверждение получения ответа клиентом.

Значения секретов, описания, тела запросов/ответов, Authorization, Cookie, CSRF,
пароли, приватные ключи и полный токен не логируются. Путь ограничен 2048 символами.
Просмотр — раздел аудита администратора или `audit.list`; события хранятся 90 дней.
Массовые операции разбиваются на записи не более 200 объектов с общими requestId
и traceId; страницы аудита ограничены числом записей и размером транспорта.
Отказы rate limit тоже сохраняются, поэтому необходимо контролировать свободное
место: срок хранения не является квотой диска. Если запись HTTP-аудита в SQLite
невозможна, сервер пишет безопасную запись в журнал ASP.NET Core с уровнем Error
и возвращает 503, если ответ ещё не начат. Команда не коммитится без своего аудита.
TLS handshake и запросы, отвергнутые Kestrel до middleware, проверяются по журналам
Kestrel/reverse proxy и не попадают в прикладной аудит.

Нужны rate limits, лимиты тела до аллокаций, ограничение параллельных запросов,
таймауты, disk-full обработка, readiness и проверенный restore.
Readiness проверяет БД и keyring без раскрытия секретов. При невозможности сохранить
изменение или его audit-событие запрос завершается ошибкой, не ложным успехом.

## 10. Разработка и сборка

Контракт хранится в `docs/protocol.md` и `docs/openapi.json`.
Сервер, UI, C# SDK и Go CLI развиваются совместно; изменения не требуют

## 11. Критерии приёмки

- Вход/выход/смена пароля, первичная настройка и CSRF проверены browser E2E.
- CRUD бакетов/секретов работает из UI, C# и Go CLI, включая пустые значения и Unicode.
- Для каждой строки матрицы проверены разрешение, отсутствие каждого обязательного
  scope и чужой бакет. QA-токен не читает и не перечисляет production.
- Повторное создание имени не восстанавливает старые grants. Проверены атомарное
  создание с выдачей доступа, expiry на границе UTC и отзыв под конкурентной нагрузкой.
- `ReadBucket` отдаёт целостный snapshot при одновременных записях. Проверены
  revisions, конфликты, лимиты, pagination и защита от случайного recursive delete.
- В перехвате HTTP-тел на доверенном proxy значения отсутствуют в открытом виде
  в обе стороны; Authorization и метаданные отдельно учитываются в модели доверия.
- Изменённые JWE, неправильный ключ, повтор, старый запрос, неподдерживаемая версия
  и подмена request ID не приводят к выполнению команды/принятию ответа.
- .NET и Go проходят одинаковые опубликованные векторы и взаимное шифрование;
  браузерный модуль проходит их же для используемых операций UI.
- Отзыв токена не ломает расшифровку другим токенам. Restore требует keyring;
  смена ключей, перезапуск, disk full и backup/restore проверены отдельно.
- ASP.NET-пример запускается со всем бакетом, ошибкой при регистровых коллизиях
  и без частичного provider при сбое. CLI exec не меняет окружение родителя.

Реализация и воспроизводимые проверки находятся в репозитории. Независимый
криптографический аудит не проводился; локальные проверки не заменяют проверку
реального развёртывания. Межъязыковая совместимость проверена для .NET, Go, Python и браузера.
