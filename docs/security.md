# Защита DarkVault

Защита приложения работает на Windows, Linux и macOS, без обязательного reverse
proxy, Fail2ban, OIDC или KMS. Внешняя инфраструктура настраивается владельцем.
API и админка могут быть публичными; HTTPS обязателен.

## Лимиты и блокировки

До проверки токенов, доступа к SQLite и JWE применяются общий лимит и лимит
источника. После аутентификации действует независимая квота токена или
администратора. Очереди нет. Ответ `429` содержит `Retry-After` в секундах.

| Переменная окружения | Значение по умолчанию, запросов в минуту |
| --- | --- |
| `Security__RateLimits__Global` | 3000 |
| `Security__RateLimits__Ip` | 300 |
| `Security__RateLimits__Principal` | 300 |
| `Security__RateLimits__Login` | 5 |
| `Security__RateLimits__Mfa` | 20 |
| `Security__RateLimits__Password` | 30 |

Допустимые значения — 1–100000; неверная настройка останавливает запуск.
Лимиты — стартовые защитные значения, а не результат нагрузочной калибровки
на оборудовании владельца. Общая квота ограничивает создание IP-счётчиков;
штатный .NET RateLimiter освобождает простаивающие счётчики.

IPv4-mapped IPv6 нормализуется к IPv4. IPv6-адреса одного `/64` разделяют квоту
и блокировку. За NAT квота общая для клиентов с одним внешним IP.

10 отказов пароля/MFA/recovery или 60 отказов API-токена за 10 минут блокируют
источник на 15 минут. Повторная блокировка удваивает срок, максимум до суток.
Успешный вход не сбрасывает историю нарушений. Блокировки учитываются до
аутентификации и не пишут каждый отклонённый запрос в БД. Хранятся максимум
8192 источника; при заполнении списка новые источники получают `429`, действующие
блокировки не вытесняются. История удаляется после суток без ошибок и окончания бана.
Состояние локально одному процессу и сбрасывается при перезапуске. Не используйте
перезапуск как автоматическую реакцию на `429`.

Одновременно допускаются две проверки пароля и 64 операции execute.
Kestrel ограничивает соединения до 256, заголовки до 16 KiB/64 полей,
время заголовков до 10 секунд. Сохраняются ограничения тела и времени запроса.
Эти ограничения не защищают от насыщения внешнего сетевого канала.

## Доверенные прокси

По умолчанию forwarded-заголовки игнорируются. Для TLS termination задайте
`DARKVAULT_TRUSTED_PROXIES` списком точных IP непосредственно подключающихся прокси,
например `127.0.0.1,::1` для локального Caddy/nginx. Принимается только один
проверенный hop; прокси должен формировать корректные `X-Forwarded-For` и
`X-Forwarded-Proto`, очищая недоверенные клиентские значения. Не включайте
автоматическое доверие forwarded-заголовкам средствами окружения ASP.NET Core.

Backend должен быть доступен только доверенному прокси либо принимать HTTPS
напрямую. При ошибочной конфигурации клиентские IP могут объединиться в одну
квоту или стать подделываемыми. Схему сети и firewall проверяет владелец.

## Администратор: пароль и passkey

Пароль больше не создаёт административную сессию. После него обязателен passkey
с проверкой пользователя: системный PIN/биометрия либо поддерживаемый аппаратный
ключ. Используется штатный WebAuthn verifier .NET 10. Нужны современный браузер
и HTTPS-домен; IP-адрес вместо домена может не поддерживаться аутентификатором.

При первом входе создайте passkey. Пока регистрация не завершена, читать секреты
и управлять хранилищем нельзя. Зарегистрируйте первый фактор в контролируемом
окружении до передачи пароля или открытия доступа посторонним.
`DARKVAULT_PUBLIC_ORIGIN=https://vault.example.com` закрепляет канонический origin
и обязателен для развёртывания за proxy. Без него origin берётся из Host запроса,
и принимается только loopback-хост; иначе passkey-операции отвечают `invalid_origin`.
Proxy должен сохранять исходный Host.
Перенос на другой домен требует продуманного восстановления/перерегистрации passkeys.

Challenge живёт две минуты, хранится только в памяти сервера и потребляется
однократно, включая неудачную попытку. Session и challenge cookies используют `__Secure-`, `Path=/admin`, Secure/HttpOnly/SameSite=Strict.
Одновременно хранится максимум 100 challenge. Проверяются origin, RP ID,
подпись, user verification и счётчик аутентификатора.

При первой регистрации показываются восемь recovery-кодов. Сохраните их офлайн:
в БД остаются только хеши. Код используется один раз вместе с паролем для
регистрации нового passkey взамен потерянных. До завершения новой регистрации
административной сессии нет. Восстановление и изменение факторов отзывают старые сессии.
В настройках можно добавить резервный passkey, максимум восемь.

Создание токена, удаление бакета, смена пароля и добавление passkey требуют MFA,
подтверждённой не более пяти минут назад. UI запрашивает подтверждение явно перед
этими действиями. Смена пароля также требует текущий пароль.

Если потеряны факторы и recovery-коды: владелец останавливает сервер и локально
выполняет `reset-mfa`, вводя текущий пароль без echo. Это не HTTP endpoint.
Команда отзывает сессии; при следующем входе обязательна новая регистрация.

## API-токены

Отсутствующий или `null` expiresAt означает 30 дней; явный срок не может быть
позже той же даты и времени следующего года в UTC. Бессрочная выдача убрана. Ранее выданные токены также
ограничены одним календарным годом от их CreatedAt: перед обновлением проверьте и замените старые
токены. `token.list`/`token.info` показывают эффективный срок.

Используйте отдельный токен для каждого приложения и окружения, конкретные бакеты
и минимальные scopes. Ротация: создать новый → переключить клиента → отозвать
старый. Проверка отзыва выполняется на каждом запросе. Автоматически повторять
изменяющие операции после `429` нельзя. CIDR/mTLS-привязки токенов пока не реализованы.

## Keyring и резервные копии

Значения в БД зашифрованы. Без отдельной защиты keyring его копия вместе с БД
позволяет расшифровать секреты. Приложение поддерживает переносимое шифрование
keyring AES-256-GCM случайным внешним 256-битным ключом, без KMS/TPM.

Для существующей установки остановите сервер и выполните локально:

```text
DarkVault.Server create-wrapping-key <new-private-key-file>
```

Установите `DARKVAULT_KEYRING_KEY_FILE` на этот файл **вне DARKVAULT_DATA**, затем:

```text
DarkVault.Server protect-keyring
DarkVault.Server verify
```

Для новой установки можно задать файл до bootstrap: новый keyring сразу будет
зашифрован. Значение ключа не передаётся в argv и не выводится в журнал. Файл
создаётся без перезаписи существующего. На Windows приватные файлы создаются
с owner-only ACL, на Unix — с режимом 0600; запись keyring атомарная.

Без правильного внешнего ключа зашифрованный keyring не открывается, в том числе
при восстановлении backup. Держите резервную копию ключа отдельно и проверьте
восстановление. Потеря ключа означает потерю доступа к данным. Старые plaintext
backup остаются чувствительными после включения защиты; их жизненным циклом
управляет владелец. Backup не копирует внешний ключ.

Это защищает копию каталога данных отдельно от ключа. Если атакующий читает и
данные, и внешний ключ либо управляет работающим процессом, такая защита недостаточна.
Изоляция ОС, шифрование диска, защита дампов, KMS/TPM и хранилище резервных копий —
рекомендации владельцу, а не скрытые обязательные зависимости приложения.

## Аудит и наблюдение

Операции с секретами и изменения MFA аудируются транзакционно до выдачи результата.
Сбой обязательного аудита не должен превращаться в успешную выдачу секрета.
Анонимные запросы и `429` не записываются в SQLite. События отказа аутентификации
поступают в `DarkVault.Security`, EventId 3001; успешное завершение MFA — EventId 3002.
Пароли, bearer-токены, recovery-коды, cookies и тела запросов в них не включаются.

Счётчик Meter `DarkVault.Security`, инструмент `darkvault.http.requests`, содержит
только ограниченные метки `status` и `principal_type`. Его можно подключить к
выбранному владельцем сборщику метрик. Полный аудит операций доступен в админке.
Доставку оповещений, ротацию stdout/journald, внешнюю копию аудита, Fail2ban/WAF
и DDoS-защиту настраивает владелец. Приложение не управляет firewall и системными службами.

План и оставшиеся проверки: [security-hardening-plan.md](security-hardening-plan.md).
